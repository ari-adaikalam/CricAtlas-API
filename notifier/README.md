# Cricket notifier

Private monitoring email for the Cricket API. It receives Alertmanager's webhooks, sends alerts and recovery notices, and sends one summary a day, all through Resend. It is a separate service. The API makes no outbound calls.

The tests use a local stand-in for Resend and a fake Prometheus. One live delivery is confirmed: the first scheduled daily summary reached the maintainer's inbox on 12 October 2026 (see `docs/measured_results.md`, the 25 hour soak). That confirms the scheduled summary email and nothing wider, and this README makes no claim about the other scenarios.

## What it sends

| Kind | When |
|---|---|
| Summary | Every day at the configured time (21:00 Australia/Sydney by default), including days with no traffic |
| Alert, recovery | Alertmanager fires or resolves a group |
| Digest | The circuit breaker closes after holding alerts back |
| Suppression notice | A budget used up alerts, once per UTC day |
| Email-path notice | Sending itself is failing, or has recovered |
| Host notice | Free disk space is below the critical level |

A summary states its exact period (start and end, local and UTC), the length of the period (23 h and 25 h on a daylight saving change), and marks any figure that is incomplete, may undercount after a restart, or has no data. A figure with no data is never shown as zero.

## How it is built

- **Ledger.** SQLite in WAL mode with full synchronous writes. A message is stored once, with its exact request bytes, their SHA-256 and its idempotency key, before any attempt. The start of an attempt is committed before a byte goes to Resend. A crash leaves a row in `sending`, which a restart settles by repeating the same bytes with the same key.
- **Doubt.** An attempt that ends unknown (a timeout, a reset, a 5xx) may have been accepted. While that is unresolved, a later refusal, a deadline, a digest or the end of the window cannot make the message `failed` or `expired` or give its charge back. It becomes `unconfirmed` and is listed for review.
- **Digest.** When the breaker closes, one digest is stored and the held alerts are ended in the same transaction, under a key that names the episode, so a crash cannot lose them.
- **Stale mail still counts for the digest.** Alerts that expire during an outage are not sent late, but their names and counts are kept until the digest that carries them is stored, even across a restart or a failing ledger. Maintenance (about every 10 minutes) cuts what is kept back to 200 incidents and 7 days, and the digest says how many were let go. If only that count is left, a count-only digest is sent.
- **States.** `cricket_notifier/states.py` holds the only allowed moves, and a test pins them. Accepted means Resend returned a message id. Delivery is not tracked.
- **Budgets.** The notifier's own caps (40 a day, 900 a month) sit under Resend's free limits. Summaries have a reserve, and the suppression, email-path and host notices have the last slots. What Resend reports about the whole account is kept apart and has its own headroom rule.
- **Circuit breaker.** Three failures in a row hold alert and recovery mail. One probe at a time goes out on a growing cool-down. Its state is in the ledger, so a restart does not release a burst.
- **Storage guard.** Limits on the database, the write-ahead log, unfinished bytes, the queue and free disk. A webhook that cannot be stored gets a 503, and Alertmanager retries.
- **Summaries.** Prometheus is read as raw samples of a few recorded series (`prometheus_rules.yml`, generated by `python -m cricket_notifier rules`). Totals are reset-corrected differences between boundary samples, so consecutive days add up.
- **Templates.** Jinja2 files under `cricket_notifier/templates/`, apart from the logic. Autoescape is on for HTML, and an undefined variable is an error.

## Before the first run

Prometheus must load `prometheus_rules.yml`. The summary reads the series it records. Write it with `python -m cricket_notifier rules --write PATH`, point Prometheus's `rule_files` at it, run `promtool check rules` on it, reload Prometheus, and check that the `cricket:*` series have samples. Without it the summary shows "no data" for the API figures.

## Running it

```
pip install ./notifier
python -m cricket_notifier check-config --config /etc/cricket-notifier/config.toml
python -m cricket_notifier run --config /etc/cricket-notifier/config.toml
```

`config.example.toml` lists every setting with placeholders. The Resend key and the webhook token live in separate files outside the repository and must not be readable by other users. The two secrets must differ.

Other commands:

| Command | What it does |
|---|---|
| `status` | Counts by kind and state, the breaker, storage, budgets used, and what needs review. Reads the ledger only |
| `review ID` | Marks a failed or unconfirmed message as reviewed |
| `resend ID` | Sends a failed or unconfirmed message again. After 24 hours the key has expired, and the command says a duplicate is possible |
| `rules [--write PATH]` | Prints or writes the Prometheus recording rules |

## Tests

```
cd notifier && python -m pytest tests -q
```

The suite covers crash recovery, quotas, retries, the breaker, daylight saving, reporting gaps and restarts, hostile webhook input and one real process. No test calls the real Resend.
